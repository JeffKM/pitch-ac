# 백엔드 포트폴리오 강화 — 4개 개념 (pitch-ac 측)

알고리즘 과외 선생님(백엔드 채용 경험)이 합격자 포폴에서 **좋게 본 4가지**를 기준으로,
이를 내 프로젝트에 녹이는 전략. 이 폴더는 **pitch-ac 측 적용**만 다룬다.

> 게임 백엔드(나라카 메타 서버) 설계는 **다른 레포로 이동**:
> `../naraka-valley/docs/meta-server/` (JeffKM/naraka-valley)

## 선생님이 본 4가지 (+보너스)

| #   | 항목                       | 선생님 평가                 | 핵심 의미                                              |
| --- | -------------------------- | --------------------------- | ------------------------------------------------------ |
| ①   | **Builder 등 디자인 패턴** | 👍 좋게 봄                  | 패턴 이름이 아니라 "왜 썼나(트레이드오프)"가 변별력    |
| ②   | **Spring Boot N+1 해결**   | 😐 "진부하다"               | 못해서가 아니라 **너무 흔해서** 차별화가 안 됨. 기본기 |
| ③   | **I/O 최적화**             | 👍 좋게 봄                  | N+1보다 한 단계 깊은 시스템 이해 (측정→병목→제거)      |
| ④   | **결제 파이프라인**        | 👍 제일 좋게 봄             | 멱등성·정합성·동시성 등 실무 최난도 도메인             |
| +α  | **동시성 제어**            | (한정판 구매에서 자연 발생) | 락 전략 비교 — 단독으로도 합격급                       |

> "진부함"을 벗는 열쇠는 **숫자(측정)** 와 **이유(ADR)**.

## 두 프로젝트의 역할 분담

4개 개념은 **두 곳에서 서로 다른 목적으로** 증명한다.

|        | pitch-ac (이 레포)                       | 나라카 메타 서버 (`../naraka-valley`)  |
| ------ | ---------------------------------------- | -------------------------------------- |
| 스택   | Next.js + Supabase + TypeScript          | Spring Boot 3 + JPA + QueryDSL + Redis |
| 역할   | 풀스택 역량 · 설계 사고 · 실서비스       | **백엔드 직무 키워드** 정조준          |
| 도메인 | PL 축구 데이터 플랫폼                    | 내가 Godot으로 만든 게임의 메타 서버   |
| 강점   | ① 패턴 · ③ I/O · ④ 결제(구독)            | ② JPA N+1 · ③ I/O · ④ 결제 · ⑤ 동시성  |
| 한계   | "JPA N+1" 같은 Spring 키워드는 증명 불가 | 실유저 트래픽은 부하테스트로 대체 증명 |

**결론:** 개념 4개는 pitch-ac에도 다 적용 가능하지만(3개 즉시 + 결제는 기능 추가),
Java/Spring 직무 키워드(JPA fetch join·@EntityGraph·QueryDSL·HikariCP)는
**나라카 메타 서버(별도 Spring 프로젝트)라야 정확히 증명**된다.
